# Part 1A – Sprint Capacity & Velocity Calculator

AI-Augmented SDLC (SEZG534) · Assignment 1 · Part 1A: SDD & harnessing for a deterministic application

A small command-line tool for Scrum Masters. It reads a sprint plan from a JSON file and tells you, before sprint planning, whether the planned story points fit the team's real capacity:

- full and available capacity (person-days, after leave and part-time allocation)
- average velocity of the last 3 sprints
- a capacity-adjusted forecast (rounded down)
- a verdict: `OVER_COMMITTED`, `FITS`, `UNDER_COMMITTED` or `NO_HISTORY`

Built with GitHub Spec Kit (spec-driven development) and GitHub Copilot as the coding agent, then validated with an independent harness.

## Requirements

- Node.js 20 or later (developed and tested on Node.js 24, Windows 11)
- npm (comes with Node.js)
- Git (the harness checks that `.harness/` is committed and unchanged)

## Install

From this `Part1A` folder:

```
npm install
```

This installs only development tools (ESLint and eslint-plugin-security). The app itself uses Node.js built-ins only.

> On Windows PowerShell, if `npm` is blocked by the script execution policy, use `npm.cmd` instead (for example `npm.cmd install`).

## Run the app

```
node src/cli.js report examples/worked-example.json
```

Expected output:

```
Full capacity: 35.0 person-days
Available capacity: 33.0 person-days
Average velocity: 24.0 points
Forecast: 22 points
Planned points: 25
Verdict: OVER_COMMITTED by 3 points
```

JSON output:

```
node src/cli.js report examples/worked-example.json --json
```

Other examples:

| Command | Shows |
|---|---|
| `node src/cli.js report examples/Sprint_01.json` | my own sprint file |
| `node src/cli.js report examples/no-history.json` | `NO_HISTORY` (no past sprints) |
| `node src/cli.js report examples/invalid-leave-days.json` | a validation error (exit code 1, message starts with `Error:`) |

Input file format (see `examples/worked-example.json`):

```json
{
  "sprintLengthDays": 10,
  "team": [
    { "name": "Asha", "leaveDays": 2 },
    { "name": "Ben" },
    { "name": "Chitra", "allocation": 0.5 },
    { "name": "Dev" }
  ],
  "pastVelocities": [18, 22, 26, 24],
  "plannedPoints": 25
}
```

`leaveDays` defaults to 0 and `allocation` to 1.0. `pastVelocities` is ordered oldest first.

## Run the harness

```
node .harness/run-harness.js --label <name>
```

Example: `node .harness/run-harness.js --label check-1`

The harness runs 7 gates and prints PASS/FAIL for each, plus an overall result (exit code 0 = PASS, 1 = FAIL):

| # | Gate | Checks |
|---|---|---|
| 1 | harness-integrity | `.harness/` is committed and unchanged |
| 2 | lint | `npm run lint` |
| 3 | security | `npm run security` |
| 4 | audit | `npm audit --audit-level=high` |
| 5 | unit-tests | all tests in `tests/` pass |
| 6 | contract | 14 harness-owned checks taken from the spec's acceptance criteria |
| 7 | traceability | every FR/NFR ID in `spec.md` starts at least one test name |

Each run saves its output to `evidence/harness-runs/run-NNN-<label>/` and adds a row to `evidence/harness-results.md`. When a gate fails, it also writes `feedback.md` in that run folder, which is given back to the coding agent.

**Known limitation:** the speed test (NFR-003, 50-member report under 1,000 ms) passes in normal conditions but can fail when the computer is busy (for example during screen recording), because most of the time is Node.js start-up. See `evidence/harness-log.md`.
